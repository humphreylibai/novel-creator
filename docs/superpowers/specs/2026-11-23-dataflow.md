# 数据流：设定 → 规划 → 章节 → 剧组

> 日期：2026-11-23
> 父文档：`2026-11-23-novel-system-overview.md`
> 说明：七个系统唯一的接缝。散在各自章节里看不清，所以单独成篇。

---

## 0. 一句话

> **数据层只有一份真相，不做任何权限控制。唯一的例外是演员——他没有任何查询接口，只接导演写的那段文字。**

## 1. 三层结构

```
① 数据层（真相）
   七系统共用一张断言图。所有部门都能读——因为场记知道明天要下雨、
   灯知道袖口是破的、剪辑知道这一章要让她漏底牌，这些都不是秘密，
   是剧组本该知道的。

② 章节上下文（ChapterContext）
   规划层的产物。所有查询都以它为入口，且带时间。

③ 部门产出
   规定情境（导演写）／置景单（场记）／造型单（灯光妆造）／
   剪辑意见（剪辑）／实录（演员）
```

## 2. 谁读什么

| 角色 | 读的方式 | 读什么 | 产出 |
|---|---|---|---|
| **导演** | 直接读全部 | 章卡、事件真相与视角、人物、势力、地理、台账 | 分镜、规定情境、审查意见、终审签字 |
| **场记** | 直接读 | `placeAt` + `ledger` | 置景单 |
| **灯光妆造** | 直接读 | `profile.外观` + `ledger`（伤 / 衣着） | 造型单 |
| **剪辑** | 直接读 | 实录 + 章卡 + 集 + 时间轴 | 剪辑意见 |
| **演员** | ✗ **无接口** | 只读导演写的「规定情境」 | 表演 |

**唯一的结构性约束是最后一行。** 不是靠过滤，是靠“演员这个环节根本没有取数入口”。

## 3. 章节上下文

```ts
ChapterContext {
  chapterId, volumeId, episodeId
  sceneIds                      // 本章这几场
  time: { year, season, day }   // ★ 所有查询都带时间
  placeId
  povCharId                     // 视角人物
  onStage: charId[]             // 在场
  lines: lineId[]               // 本章推进的故事线（主线 + 副线）
  events: eventId[]             // 对应编年史里的哪些事件
  mustChange, mustLeave, forbidden   // 只给导演与剪辑
}
```

`time` 是天然的时间闸：同一个查询，带 `time` 就拿不到未来的东西。

## 4. 查询接口（按归属系统）

| 函数 | 归属 | 返回 |
|---|---|---|
| `ctx(chapterId)` | L5 篇章 | 章节上下文 |
| `profile(charId, at)` | L2 人物 | 底盘 + 状态段 + 语域 + 外观 |
| `beliefsOf(holder, at)` | L0 世界观 / L3 编年史 | 他相信什么（含信错的版本） |
| `perspective(eventId, holder)` | L3 编年史 | 某事件在某视角下的版本 |
| `truth(eventId)` | L3 编年史 | 事件真相 |
| `relationsOf(entityId, at)` | L2 人物 / 势力 | 关系边（表面层，另可查真相层） |
| `placeAt(placeId, at)` | L1 地理 | 地形、气候、时辰、归属 |
| `ledger(at, placeId?)` | L6 创作 | 连续性台账（伤 / 道具 / 知情 / 承诺） |
| `knotsOpen(subjectId?)` | L4 事件 | 未解的结与张力 |

**这些函数谁都能调。** 只有演员不调——因为它不取数。

## 5. 导演写规定情境时，每一行从哪来

| 情境里那一行 | 查询 | 源 |
|---|---|---|
| 你是谁 | `profile(me).底盘` | L2 人物底盘 |
| 这一场 | `ctx(ch).mustChange` 的**局部化改写** | L5 章卡 → 导演改写 |
| 你不能 | `profile(me, at).底线` | L2 状态段 |
| 你怕 | `profile(me, at).恐惧` | L2 状态段 |
| 你以为 | `perspective(event, me)` + `beliefsOf(me, at)` | L3 / L0 视角层 |
| 你欠着 | `relationsOf(me, at)` 中类型为「债」的边 | L2 关系边 |
| 此刻 | `ledger(at, place)` + `placeAt` 的公开部分 | L6 台账 + L1 地理 |
| 你说话 | `profile(me).语域` | L2 底盘 |

**没有一行来自 `truth()`。** 导演查真相是为了调度，不是为了转述。

## 6. 数据流全景

```
L0 世界观 ─ 公理/代价 ─┐
L1 地理   ─ placeAt ──┤
L2 人物   ─ profile/  ─┼──▶ ChapterContext ──▶ 部门产出
L2 势力   ─ relations ─┤        ▲                  │
L3 编年史 ─ perspective┤        │                  ▼
L4 事件   ─ knotsOpen ─┘    章卡(L5)            实录 / 各单子
                                                     │
                              ┌──────────────────────┤
                              ▼                      ▼
                    连续性台账（伤/道具/知情/承诺）  剪辑意见 → 导演审查
                              │                      │
                              └──────────┬───────────┘
                                         ▼
                                    终审签字 → 正文（作者采纳）
                                         │
                    ┌────────────────────┼────────────────────┐
                    ▼                    ▼                    ▼
              belief 更新          关系 / 结变化         新专名 → 建条目
              （回 L0/L3）         （回 L2/L4）         （回 L0）
```

## 7. 回流规则

> **只有正文里真的写出来的东西才回流。**

没采纳的实录、被退回的置景单、剪辑砍掉的意见，都不改任何数据——否则世界会被草稿污染。

| 回流源 | 回流目标 | 触发 |
|---|---|---|
| 正文里的行为 | 人物状态段（若打破底线 → 🔴 三选一） | 采纳 |
| 正文里的物理事实 | 连续性台账（伤、道具、时间、在场） | 采纳 |
| 正文/实录里的认知变化 | `belief`（holder、置信度） | 采纳 |
| 实录里产生的结 | L4 事件（新增结） | 采纳 |
| 正文里出现的新专名 | L0 条目（未定义专名扫描） | 采纳或手动 |

## 8. 三个对象，没有第四个

| 对象 | 谁写 | 性质 |
|---|---|---|
| **规定情境** | 导演 | 唯一由人写、不来自查询的分发物 |
| **实录** | 各部门 | 带三色标记（⚠ 错 / ◇ 素材 / ✂ 建议） |
| **连续性台账** | 系统累积 + 场记维护 | 由已采纳的正文自动生成 |

之前设计过的「掩码子系统」「权限矩阵」「函数白名单」「信息包构建器」**全部删除**——信息可见性是导演的职责，不是数据层的机制。

## 9. 为什么这条链是可行的

| 保证 | 靠什么 |
|---|---|
| 演员不会剧透 | 他没有接口；他只读导演写的文字 |
| 各部门知道该知道的 | 他们直接读数据（环境、外观、结构都不算秘密） |
| 数据不被草稿污染 | 只有采纳后的正文才回流 |
| 改稿不崩 | 连续性台账 + 既定度 + 引用反查 |
| 过程可回溯 | 每章一份 `chapter-prod/`，全部进 git |
